# Design Bible Playbook

Standing playbook for building and enforcing a design system on any app, website, or
design refresh. This is the reusable process — run it once per project, then keep the
resulting files current as the project evolves. It exists to close one gap: **agents
have been making independent styling decisions (hardcoded hex, ad hoc spacing, no
component reuse) because nothing stopped them.** This playbook removes that freedom
structurally, not by asking nicely.

**Origin:** written 2026-09-11 during the claude-god architecture session that
diagnosed this gap. First applied to the Vanyshr app.

---

## 0. The core diagnosis

Documentation alone does not work. `role-frontend-engineer` has said "read the design
system before inventing" for a while — it was advisory, and agents still hardcoded
hex codes. The fix is not a better-written doc; it's removing the option to freestyle
at three separate layers (context, tooling, and enforcement) so no single layer being
skipped lets a violation through.

**Success criterion:** an agent handed an unstyled wireframe should be able to
implement it with zero styling decisions of its own — every color, space, type role,
radius, shadow, and component comes from a named token or an existing component, never
invented in the moment.

---

## 1. File architecture

Three tiers. Don't add files beyond this list — more files means more places to go
stale.

### Tier 1 — Master spec (Maiztro Library level, cross-project)

```
Maiztro-Library/DesignSystems/{brand}/
  design-system.md   ← canonical brand-level spec, generated by design-system-extractor
  tokens.json         ← exportable token format
  components.md       ← component registry (brand-level, if shared across apps)
```

Source of truth for brand identity when a brand spans multiple apps. Not every project
needs this tier — single-app projects can skip straight to Tier 2 and treat it as both
master and implementation.

### Tier 2 — Project implementation (every app/website repo, no exceptions)

```
docs/
  DESIGN.md          ← the bible. Every frontend agent reads this before touching UI.
  COMPONENTS.md       ← component catalog: name, import, variants, code example, when (not) to use
src/styles/            ← or wherever the project's CSS lives
  tokens.css           ← THE only place raw color/space/type values are allowed to live
CLAUDE.md              ← existing project file; gets a ## Design section (see §3)
```

This tier is mandatory for every project this playbook is run against. `DESIGN.md`
and `COMPONENTS.md` are separate files because DESIGN.md is always-required reading
(kept short enough to read every time) while COMPONENTS.md is loaded on demand when a
task touches a specific component type.

### Tier 3 — Enforcement tooling (machine-level, shared across all projects)

```
~/.claude/hooks/
  design-token-guard.py   ← PreToolUse hook; blocks raw hex/spacing writes to UI files
~/.claude/settings.json   ← wires the hook to Edit|Write on UI file globs
```

One shared hook serves every project — it reads each project's own `docs/DESIGN.md`
§10 (Anti-patterns) to know what to flag, so it doesn't need per-project
configuration beyond that file existing.

## 2. DESIGN.md — required sections, in order

Write for agents, not humans. Rules stated as rules, not suggestions. This exact
section order, every time. §0–§11 are required for every project; §12 is optional
and appears only when the product actually has bespoke, non-tokenizable effects.

**Headers are literal, not paraphrased.** Every project's DESIGN.md uses
`## {n} {Title}` as defined in `docs/bible-language.md` (e.g. `## 2 Color`) —
not `## §2 — Color Tokens` and not a project-specific rename like
`## Color Palette`. The format is identical and machine-checkable across every
project; a tool checking for completeness (or an agent skimming for 0 Quick
Reference) matches on the number + title, not a paraphrase.
Content specific to one project that has no numbered slot (e.g. a "Component rules"
list of do's/don'ts for this product's buttons) can still exist as an unnumbered
section — it's paraphrasing an *actual* numbered section that's not allowed.

**Cross-cutting rule: when a pattern can't be reduced to a token or a short recipe,
embed a real code snippet as the reference implementation.** A prose description of
a shader or a complex interaction is lossy; a working code sample isn't. This applies
wherever it's needed, not just in §12 — a bespoke chart interaction or a non-standard
focus trap earns the same treatment.

### §0 — Quick Reference
The only section every agent is guaranteed to read in full. Contents:
- **Composition archetype, one line, first thing in the file:** layout type
  (grid / full-bleed / boxed / sidebar+content), content width, and framing
  material (flat / glass / skeuomorphic). Lets an agent orient to the
  structural frame before it ever reaches a token — catches a "boxed
  dashboard vs. full-bleed marketing page" mismatch before it becomes a
  rebuild.
- Flat list of all token names (names only, not values) grouped by category
- The hard rules, in bold, restated from §3 of this playbook
- Links to `tokens.css` and `COMPONENTS.md`
- Flat list of available component names

### §1 — Principles (≤5)
Foundational, non-negotiable rules that resolve cases the spec doesn't explicitly
cover — e.g. "One accent color carries every primary action," "Status reads as
outline, not fill." These exist so an agent facing an undocumented edge case has a
principle to reason from instead of a blank slate.

### §2 — Color Tokens
- The literal `:root { --token: value; }` CSS block (mirrored verbatim in
  `tokens.css` — DESIGN.md and tokens.css must never drift apart)
- A semantic table: **Token | Semantic purpose | Where used | Where it must NOT be used**
- An explicit forbidden list feeding §10 and the PreToolUse hook: raw hex, `rgb()`/`rgba()`
  literals, CSS color names

### §3 — Typography
Named roles, not bare sizes. Table: **Role | Family | Size token | Weight | Line
height | Where used**. Agents write `var(--size-body)`, never `16px`.

### §4 — Spacing
Base unit declaration (4px or 8px) plus a named scale with px equivalents
(`--space-1` through `--space-16` or similar) and usage guidance — when to reach for
which step (intra-component gap vs. inter-component gap vs. section separation).
This is the section most existing design docs skip; it is not optional here.

### §5 — Layout
Container max-widths, named breakpoints, grid/column system, responsive stacking
rules.

### §6 — Elevation, Borders, Radius
Named shadow levels, named border-radius scale, and a border-emphasis ladder (rest →
hover → emphasis → status-outline) if the product uses one.

**Named technique recipes.** Some visual effects can't be reduced to a single
token — they're a construction sequence. When one recurs (a gradient-border shell,
a frosted-glass card stack, a specific glow treatment), give it a name and write the
recipe as steps ("wrap the surface in an outer shell with Npx padding and 0 radius,
drive the border with a gradient, inset the real content at a slightly smaller
radius so the gradient reads as a hairline frame"), not just a shadow value. Agents
copy the recipe; they don't reverse-engineer the effect from a screenshot.

### §7 — Motion
Duration scale (`--duration-instant/fast/base/slow/slower`), named easing curves
(`--ease-standard/emphasized/decelerate/accelerate/linear`), and the
`prefers-reduced-motion` rule.

- **Motion intensity — one named level for the whole product:** subtle /
  moderate / bold. Gives agents a ceiling to check new animation ideas against
  without re-deriving "how much motion is too much" per component.
- **Hover-property taxonomy:** the explicit list of CSS properties allowed to
  animate on hover (e.g. text, color, shadow, opacity) — and, by omission,
  which are not (transform/scale, unless stated). Prevents one component
  getting a bounce-scale hover while its neighbor gets a color fade.
- **Scroll-pattern convention**, if the product uses scroll-driven reveals:
  name the actual technique/library in use (e.g. "IntersectionObserver + CSS
  transition," "GSAP ScrollTrigger") so agents extend the existing pattern
  instead of introducing a second scroll-animation system.

### §8 — Icons
Library/package, import pattern, named sizing scale, contextual usage rules.

### §9 — States
Token assignments for hover, focus, active, disabled, loading, and error states —
defined once, referenced everywhere, so buttons/inputs/cards don't each reinvent
their own hover behavior.

### §10 — Anti-patterns (the enforcement ground truth)
Two tiers, kept visually separate — they're validated differently.

**§10a — Mechanical (hook-enforced).** Concrete, regex-able, checked by the
PreToolUse hook or pre-commit guard automatically — a violation here is blocked
before it lands, not just discouraged:
```
NEVER in component files:
- Raw hex (#282828, #14ABFE, ...)
- rgb() / rgba() with literal values
- CSS color names (red, blue, gray, ...)
- Arbitrary utility values (text-[#666], p-[13px])
- Inline style attribute carrying color or spacing values
- Font sizes in px not on the type scale
- New font families not declared in §3
- Raw z-index values (use named levels)
- Hardcoded breakpoint values (use named breakpoint tokens)
```

**§10b — Judgment (agent self-checked, not mechanically enforceable).** No hook
can regex-match "used discretion badly" — these rely on the agent reading and
applying them, which is exactly why they need to be spelled out explicitly rather
than left implicit:
```
- Don't introduce a new accent color outside the core palette without a
  genuine new semantic state to justify it.
- Don't mix shadow/blur/elevation recipes that don't already coexist
  elsewhere in the product — reuse an existing depth recipe.
- Don't exceed the stated motion intensity (§7) without a deliberate,
  stated reason.
- Don't invent a new component when an existing one in COMPONENTS.md
  covers the case with a different prop/variant.
```

### §11 — Component Reference
One line per component (name, file path, variants, one-line usage note); the full
catalog with code examples lives in `COMPONENTS.md`, linked from here.

### §12 — Bespoke Effects (optional — include only if applicable)
For products with custom canvas/WebGL/shader work, or any other effect too one-off
to tokenize. Document: scene/effect name, core primitives, motion character,
interaction behavior (pointer-reactive, static, etc.), render approach (DPR
clamping, custom shaders, library used), and named techniques. Embed the actual
reference code (HTML structure + the core JS/shader source) directly in the doc per
the cross-cutting rule in §2 — not just a prose description. Skip entirely for
products without this kind of work (e.g. Vanyshr's dashboard has no use for this
section; a ringldr marketing page with a shader hero would).

## 3. Guardrails — the enforcement stack

Five layers, weakest to strongest. All five get built; skipping any one reopens the
exact hole this playbook exists to close.

### Layer 1 — CLAUDE.md `## Design` section
Add verbatim to the project's CLAUDE.md:

```markdown
## Design

Read `docs/DESIGN.md` BEFORE writing or editing ANY UI code. No exceptions.
If DESIGN.md does not exist at that path, STOP — do not proceed with styling.

Hard rules:
- No raw hex, rgb(), or rgba() in component files — use `tokens.css` custom props.
- No arbitrary px values for spacing — use the spacing scale (DESIGN.md §4).
- No font families not in DESIGN.md §3.
- No `style={{ }}` with color or spacing values — use className and tokens.
- When a component exists in `docs/COMPONENTS.md`, use it. Do not reinvent.
- When ambiguous, STOP and ask. Do not make a design decision independently.

Token file: `src/styles/tokens.css`
Component catalog: `docs/COMPONENTS.md`
```

Cheapest layer to add; catches most violations because agents read CLAUDE.md before
acting.

### Layer 2 — Skill-level gate
`frontend-engineer` and `role-frontend-engineer` get a mandatory step 1 with a bail
condition:
```
1. Confirm docs/DESIGN.md exists. If not: stop and report — do not proceed.
2. Read DESIGN.md §0 (Quick Reference) in full.
3. Read COMPONENTS.md for any component type the task touches.
4. Only then begin implementation, using named tokens exclusively.
```

### Layer 3 — PreToolUse hook (hardest enforcement)
`~/.claude/hooks/design-token-guard.py`, wired via `settings.json` on `Edit|Write`
matched to UI file globs (`.tsx`, `.jsx`, `.vue`, `.svelte`, `.css`). Reads the tool
call's file path + new content from stdin; if the file is a UI file, scans for the
§10a forbidden patterns (the mechanical tier — §10b is judgment-only and isn't
hook-checkable); on a hit, exits non-zero with a message naming the violation and
the token to use instead, which blocks the write outright.

This is the only layer that makes a violation structurally impossible rather than
merely discouraged — it fires before the file lands, not after.

### Layer 4 — Design compliance audit
Extend `frontend-auditor` (or add a `design-auditor` pass) to run post-implementation:
grep changed files for §10a's forbidden patterns (the same regex set as the hook) to
catch anything written before the hook existed or in files that didn't pass through
Edit/Write, and separately walk §10b's judgment list by eye/model-review since it
isn't regex-checkable. Report violations of either tier with the correct fix.

### Layer 5 — Component library (removes the decision, not just the violation)
`COMPONENTS.md`, populated with every reusable primitive (Button, Input, Card, Modal,
etc.) as name + import path + variant code example + one-line usage note. When a
component is documented and required, agents stop building bespoke one-offs — the
freestyle option disappears rather than being merely forbidden.

## 4. Standard run order

Apply this sequence to any project — new or existing:

1. **Source the spec.** If visual references exist (screenshots, an existing app,
   Figma exports), run `/design-system-extractor` against them → writes to
   `Maiztro-Library/DesignSystems/{project}/`. If a `docs/DESIGN.md`-shaped doc
   already exists for the project (as with Vanyshr's `design-sandbox/design.md`),
   treat it as the starting draft instead of extracting from scratch.
2. **Fill DESIGN.md against §2 of this playbook.** Add whatever sections are
   missing — spacing and anti-patterns are the most commonly missing.
3. **Write/sync `tokens.css`** so it's byte-identical in substance to DESIGN.md §2's
   CSS block. If a JS/TS token file already exists (e.g. `tokens.js`), convert or
   mirror it — CSS custom properties are the enforcement surface, so they must exist
   even if a JS layer also does.
4. **Add the `## Design` section to the project's CLAUDE.md** (Layer 1).
5. **Confirm/patch the PreToolUse hook** is wired for this project's file globs
   (Layer 3) — one shared hook script, no per-project copy needed.
6. **Patch `frontend-engineer` / `role-frontend-engineer`** with the bail condition
   if not already present (Layer 2) — this is a one-time library-level change, not
   per-project.
7. **Build `COMPONENTS.md`** from whatever component inventory already exists
   (Layer 5).
8. **Run a design-compliance audit pass** (Layer 4) over existing code to catch
   pre-existing violations — expect this to surface a punchlist on the first run of
   any project that predates this playbook.

Steps 5–6 happen once and then apply to every future project automatically. Steps
1–4, 7–8 are per-project.

---

## 5. Definition of done

A project is "on the design bible" when all of the following hold:

- [ ] `docs/DESIGN.md` exists and has all 12 required sections (§0–§11) filled, not
      stubbed — plus §12 (Bespoke Effects) if the product has that kind of work
- [ ] `docs/COMPONENTS.md` exists and covers every reusable UI primitive in the codebase
- [ ] `src/styles/tokens.css` exists and matches DESIGN.md §2/§4/§6/§7 exactly
- [ ] CLAUDE.md has the `## Design` section from §3 Layer 1 of this playbook
- [ ] The PreToolUse hook is active and has been smoke-tested (attempt a hardcoded
      hex write, confirm it's blocked)
- [ ] A design-compliance audit has been run at least once with zero unresolved
      violations
- [ ] A test: hand a frontend agent an unstyled wireframe for a net-new page and
      confirm it implements it with zero hardcoded values and zero new components
      not already in COMPONENTS.md

That last check is the real acceptance test — everything above it is scaffolding in
service of it.

---

## 6. Maintenance

- DESIGN.md and tokens.css are living documents — every time a token, spacing step,
  or component is added anywhere in the codebase, it goes into these files in the
  same commit, not after the fact.
- If a project's DESIGN.md and tokens.css ever drift (different values for the
  "same" token), tokens.css is not automatically the winner — treat it as a bug,
  reconcile by hand, and check which one is actually deployed.
- Re-run the Layer 4 audit whenever a large batch of UI work lands outside of normal
  per-PR review (e.g. after a multi-file agent-driven refactor).
